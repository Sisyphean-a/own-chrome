# 破坏性同步操作保护根因分析

## 1. 问题定位

| 关键位置 | 说明 |
|---|---|
| `src/core/application/facades/WorkspaceFacade.ts:154-156` | 删除分类先修改内存索引；删除最后分类时以 `forceOverwrite=true` 保存空索引。 |
| `src/core/application/facades/WorkspaceFacade.ts:158-180` | 分类文件清理完成后再次强制保存索引，远程并发更新不会触发冲突。 |
| `src/core/application/services/SyncService.ts:161-169` | `force=true` 时明确跳过 `ConflictGuard.assertCanPush`。 |
| `src/core/application/facades/SyncFacade.ts:45-53` | 强制拉取先清空本地，再调用 `syncDown`；异常时没有恢复路径。 |
| `src/core/application/services/sync/SyncDownCoordinator.ts:55-80` | `null` 参数会回退使用配置中的旧远程时间；同步头哈希相同也会提前返回。 |
| `src/core/application/services/sync/ShardStateService.ts:69-83` | 分片增量计算继续使用旧摘要，清空本地后仍可能只拉变化分片。 |
| `src/core/application/facades/SyncFacade.ts:85-90` | 文件、历史、索引与缓存并行清空，部分失败或后续拉取失败均无回滚。 |

## 2. 失败路径还原

### 删除最后分类

**正常路径**：用户删除分类 → 使用本地记录的远程时间检查冲突 → 远程未更新才写入索引 → 清理文件 → 使用最新远程时间提交最终索引。

**失败路径**：用户删除分类 → 本地分类数变为零 → 以强制模式写入空索引 → 跳过远程冲突检查 → 清理文件 → 再次强制覆盖索引。旧设备因此可以覆盖其他设备的新数据。

**分叉点**：`src/core/application/facades/WorkspaceFacade.ts:156` — 是否为最后分类被错误地用作跳过并发保护的条件；`src/core/application/facades/WorkspaceFacade.ts:180` 又无条件跳过保护。

### 强制拉取

**正常路径**：确认远程根存在 → 完整拉取远程索引和全部分片 → 成功后替换本地状态；失败时保留原本地状态。

**失败路径 A**：确认远程根存在 → 清空全部本地数据 → 后续网络、解析或存储操作失败 → 抛错，但本地已经为空。

**失败路径 B**：确认远程根存在 → 清空全部本地数据 → `syncDown` 继续读取配置里的旧时间、同步头和分片摘要 → 远程未变化时提前返回，或只拉取变化分片 → 操作没有报错，但本地文件未被完整重建。

**分叉点**：`src/core/application/facades/SyncFacade.ts:45-53` — 清空动作发生在完整拉取之前，且“force”只把方法参数设为 `null`，没有失效配置中的增量同步标记。

## 3. 根因

**根因类型**：并发 / 竞态为主，兼有状态污染与缺少防御。

**根因描述**：分类删除把“允许清空索引”与“允许跳过远程冲突检查”混为同一条件，并在多步骤操作末尾继续强制覆盖。强制拉取则把清空和下载拆成不可回滚的两个阶段，同时仍携带用于增量同步的旧状态，因此既不能保证失败原子性，也不能保证成功时执行完整拉取。

**是否有多个根因**：是。

1. 主因：破坏性写入跳过远程并发检查。
2. 次因：强制拉取没有本地恢复点。
3. 次因：强制拉取没有清除时间、同步头和分片摘要三个增量标记。
4. 次因：分类索引在首次远程写入成功前已修改，冲突失败时未恢复内存状态。

## 4. 影响面

- **影响范围**：删除任意分类的最终索引提交都绕过冲突；删除最后分类还会在首次提交时绕过冲突。所有强制拉取都受旧增量标记影响，远程未变化时风险最高。
- **潜在受害模块**：工作区分类管理、远程索引、分片状态、IndexedDB 文件、IndexedDB 历史、浏览器本地索引与缓存、前端当前选择状态。
- **数据完整性风险**：有。远程可能被陈旧空索引覆盖；本地可能在失败后为空，或出现“索引存在但部分文件未重新下载”的不一致状态。
- **严重程度复核**：维持 P0。第二项可覆盖远程较新数据；第三项不只影响失败场景，在远程未变化时也可能稳定触发空本地或不完整重建。

## 5. 修复方案

### 方案 A：恢复点 + 完整强制拉取 + 乐观并发检查

- **做什么**：分类删除不再传 `forceOverwrite`；保存首次写入返回的远程时间，文件清理后用最新时间进行最终冲突检查；首次保存失败时恢复内存分类。强制拉取前由三个本地仓储分别创建内存恢复点，清除配置副本中的远程时间、同步头哈希和分片摘要后执行完整拉取；任何异常都恢复文件、历史、索引和缓存。
- **优点**：直接修复已确认根因；保持现有同步和仓储分层；正常操作语义不变；可通过依赖注入编写确定性单测。
- **缺点 / 风险**：拉取期间需要在内存保存一份本地快照；浏览器进程直接崩溃时内存恢复点无法执行；恢复本身失败时必须显式抛出组合错误。
- **影响面**：`WorkspaceFacade`、`SyncFacade`、三个本地仓储及对应测试；不修改远程分片清理语义。

### 方案 B：远程暂存后原子替换本地

- **做什么**：重构 `SyncDownCoordinator` 与 `ShardPullService`，先把完整远程索引和全部文件下载到暂存结果，不触碰现有本地数据；下载全部成功后，用 IndexedDB 事务替换文件和历史，再更新浏览器存储中的索引与缓存。分类删除仍改为非强制冲突检查。
- **优点**：下载失败天然不影响本地；同步过程语义更接近事务；无需在内存中同时保留新旧两份实体对象以外的恢复闭包。
- **缺点 / 风险**：改动同步核心调用链，影响面明显更大；IndexedDB 与 `chrome.storage` 无法组成真正的跨存储事务，仍需处理提交中途失败；回归测试成本高。
- **影响面**：同步协调器、分片拉取、仓储端口、基础设施和测试。

### 方案 C：只延后清空并取消强制覆盖

- **做什么**：先执行现有拉取，成功后再清理历史和缓存；分类删除只移除两个 `forceOverwrite`。
- **优点**：改动最小。
- **缺点 / 风险**：现有拉取会写入本地文件，途中失败仍可能产生新旧混合状态；不建立恢复点；无法完整解决数据一致性问题。
- **影响面**：主要是两个 facade，但保护不完整。

### 推荐方案

**推荐方案 A**。它直接覆盖远程冲突、强制全量拉取和异常恢复三个根因，改动集中在现有职责边界内，风险和回归范围显著小于重构同步核心，同时比仅调整调用顺序提供完整得多的失败保护。
